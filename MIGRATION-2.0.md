# .NET SDK 2.0 migration

Version 2.0 changes capture and hook timing. Keep a pinned 1.x installation available during rollout. All `DebugBundle.*` packages in an application must use the same version.

Configured `RandomSource` sampling runs on the existing sender before `BeforeSend`; retry delivery does not resample an accepted event. Framework logging alignment and numeric precision above 256 use the safe message fallback to bound formatting allocations.

Capture now checks the effective local and remote log/request policy before building an event. `BeforeSend` is invoked on the sender worker for admitted events, after the privacy-safe capture snapshot and before transport. It does not observe filtered or sampled-out events and must not depend on request-thread state or mutable application objects. A failed or slow callback cannot hold an application capture caller. The initial remote configuration fetch is asynchronous; until it completes, the connected client uses a restrictive policy and may omit early low-severity records.

Automatic delivery uses one sender with coalesced wakeups and at most one in-flight transport operation. `FlushAsync` waits for this sender up to `RequestTimeout` and can be cancelled by the caller; a timed-out wait does not cancel the shared sender. At most 64 callers can retain an explicit flush wait at once; additional calls complete immediately while the sender is saturated. Completion means the wait ended, not that ingestion accepted every event. The pending queue holds at most 512 captured events. Pending and in-flight captured events, final hook replacements and suppression aggregates share a 1,000-event/8 MiB budget; ordinary logs and requests may use at most 800 of those event slots so an incident has room during a low-priority burst. When overloaded, lower-priority logs and ordinary requests yield to exceptions and failed requests; omitted counts become bounded `error_suppressed` operational aggregates with `reason: queue_pressure` and a `level` class. A 429 or retryable response schedules a background retry after its backoff period. Telemetry can still be lost under sustained overload to protect the host.

Exception capture snapshots ordinary base `Exception` message/stack/inner/HResult fields without invoking overrides. Custom `Message`, `StackTrace`, and `ToString` projection runs on the existing sender, using only a weak reference to the original exception. If it has been collected, the safe snapshot remains; unavailable custom details are reported as `Exception details unavailable`. Custom getters can delay that sender, but cannot hold capture or explicit flush callers. No strong application exception graph is queued.

The Microsoft logging provider preserves standard message templates, primitive arguments, structured fields and ordinary dictionary scopes. Application formatters with reference-type state execute on the sender through weak references; collected state/formatters retain the safe snapshot. Custom value-type state formatters are not invoked and use `Log details unavailable` (or the safe exception message). Custom object template arguments use `[Unsupported value]`. Custom external scope providers are omitted. Custom `IDebugBundleClient` implementations receive the primitive snapshot without deferred enrichment.

Telemetry context and probe values support primitives, JSON elements, exact standard `Dictionary<string, T>`, `List<T>`, one-dimensional arrays, `Hashtable` and `ArrayList`. Custom collection subclasses/wrappers and arbitrary object properties are not enumerated or reflected; they use `[Unsupported value]`. Convert application objects into a bounded dictionary of primitives before capture. All accepted snapshots and deferred output still pass mandatory privacy protection before hooks and again before delivery.
